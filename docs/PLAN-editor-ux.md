# Design Canvas — план улучшения редактора

Анализ и порядок работ по пяти запросам: подсветка при наведении, направляющие
(статичные и динамичные), замеры отступов, дополнительные удобства редактирования,
переработка системы компонентов. Документ — рабочий план, а не описание реализации:
источник правды по факту сделанного — [README.md](../README.md) и
[docs/ARCHITECTURE.md](ARCHITECTURE.md), найденные дефекты — [BACKLOG.md](BACKLOG.md).

Статус фаз отмечен в конце раздела 7. Ничего из перечисленного не считается
сделанным, пока не пройдены `npm run check` и `npm test` и не обновлены README
(поведение для человека) и ARCHITECTURE (слой, если менялась модель документа).

## 2. Подсветка при наведении (структура)

Сейчас холст — «плоская картинка»: чтобы понять, что за объект под курсором и чему он
принадлежит, нужно кликнуть и смотреть в дерево слоёв. Цель — читать структуру не кликая.

Что показываем при наведении:

1. **Обводку наведённого узла** (1px, непрозрачная) и **подпись рядом с курсором**:
   имя, тип, размер (`W×H`), для инстанса — ключ компонента.
2. **Цепочку предков**: каждый контейнер от наведённого узла до верхнего фрейма получает
   тонкую пунктирную обводку и подпись у левого верхнего угла. Это и есть «понимание
   структуры»: видно, что кнопка лежит внутри карточки, а карточка — внутри экрана.
3. **Синхронизацию с деревом слоёв**: строка наведённого узла подсвечивается, предки
   получают приглушённую метку. Это работает и в обратную сторону (наведение в дереве
   подсвечивает узел на холсте) — дёшево, потому что состояние одно.
4. Обводка **не мешает выбору**: оверлеи наведения рисуются поверх, `pointer-events: none`.

Почему в экранных координатах. Оверлеи наведения и замеров рисуются в слое, который не
масштабируется: толщина линии и кегль подписи остаются постоянными при `zoom ≠ 1`, а текст
не мылится. Для этого нужен один обход дерева, дающий **абсолютные прямоугольники всех
узлов сразу** (`flattenRects(root) → { rects, parents, order }`) — сейчас `absRect` ищет
один узел за полный обход, и на наведении это было бы O(n) на каждое движение мыши.

## 3. Направляющие

### 3.1 Статичные направляющие пользователя

Хранятся **в документе**, а не в localStorage: линейка — часть макета, её хочется
закоммитить и увидеть у коллеги, а «пропавшие» после перезагрузки направляющие — источник
расхождений. Место — новое поле документа:

```json
"guides": { "x": [120, 340], "y": [64] }
```

`x` — вертикальные линии на этой координате X, `y` — горизонтальные. Поле нормализуется
(`finite`, сортировка, дедупликация, лимит 100 на ось), переживает запись из панели,
игнорируется экспортом (в HTML не попадает: это редакторская разметка, как в Figma) и
доступно агенту операцией `set-guides`.

UX:

- **Линейки** сверху и слева вьюпорта, с шагом, зависящим от масштаба (между штрихами
  8–40 экранных пикселей), с подписями каждые 100 мировых пикселей.
- **Создание**: потянуть из линейки — появляется направляющая и тянется за курсором.
- **Перенос**: тянуть саму линию (у неё широкая невидимая зона захвата, 6px).
- **Удаление**: уронить линию обратно на линейку (или за пределы холста), `Delete` при
  переносе, либо двойной клик по линии.
- **Показ/скрытие** — кнопка в тулбаре (в Figma `Shift+R`); скрытые направляющие остаются
  в документе, но не мешают.
- **Сброс** — «убрать все направляющие» рядом с переключателем.

### 3.2 Динамичные направляющие (smart guides)

Во время перемещения, ресайза и создания узла вычисляются кандидаты на выравнивание, и
объект «прилипает» к ним; совпавшие линии рисуются поверх.

Кандидаты:

| Источник | Линии |
|---|---|
| родитель | left, centerX, right / top, centerY, bottom (по внутренней рамке с `padding`) |
| соседи по родителю | те же шесть линий каждого видимого соседа |
| другие верхние фреймы | шесть линий |
| статичные направляющие | сама линия |

Алгоритм: для перемещаемого габарита берутся left/centerX/right и top/centerY/bottom; среди
кандидатов ищется ближайший в пределах порога (6 экранных пикселей, то есть `6 / zoom`
мировых). Сдвиг `dx`/`dy` доводится до кандидата; **привязка к объектам важнее привязки к
сетке**, поэтому порядок такой: сырое смещение → сетка (`snapStep`) → smart-привязка → Alt
отключает и то, и другое. Совпавшие линии рисуются от края до края задействованных узлов.

Отложено (P2, отдельная проверка): **равные интервалы** — когда три и более объекта стоят
с одинаковыми промежутками, Figma показывает значок равенства. Требует перебора пар
промежутков, а не только линий; сначала нужно убедиться, что базовая привязка не мешает.

### 3.3 Точки изменения модели

Новое поле документа (`guides`) проходит тот же путь, что новое поле узла (см.
`ARCHITECTURE.md` §13), но короче — у документа нет потребителя в `export.js`:
нормализация в `schema.js`, операция в `ops.js` + описание в `tools.js`, чтение в
`client.js`. Проверка в `smoke.mjs`: документ без поля не обрастает им, поле переживает
`normalizeDoc`, операция валидирует вход и чистит `clear`.

## 4. Замеры отступов

Что показываем и когда:

| Когда | Что видно |
|---|---|
| наведение (обычное) | обводка, подпись, **подсветка padding родителя**: четыре заливки вокруг контента с числами `t/r/b/l` |
| наведение + Alt | плюс расстояния до ближайших соседей с каждой стороны |
| узел выделен | расстояния до рамки родителя и до ближайших соседей — постоянно |
| перетаскивание/ресайз | живые расстояния до соседей и до родителя, значения обновляются на каждом кадре |

Как считаем: для узла берём абсолютный прямоугольник, прямоугольник родителя и его
`layout.padding` (у нераскладочного контейнера padding считаем нулевым). Соседи — дети того
же родителя, пересекающиеся с узлом по перпендикулярной оси; из них выбирается ближайший
с каждой стороны. Расстояние может быть отрицательным (заход за соседа) — тогда показываем
знак, а не прячем замер.

Замеры рисуются в экранных координатах, подписи — капсулой на подложке темы, чтобы читались
и в светлой, и в тёмной теме.

## 6. Система компонентов

### 6.1 Что мешает сейчас

1. **Компонент не видно.** В списке — ключ, размер, число узлов и инстансов. Что за компонент,
   как он выглядит, понять нельзя, не найдя его инстанс на холсте.
2. **Инстанс нельзя выбрать из списка.** Клик по карточке ищет первый верхний фрейм с этим
   ключом: если инстанс вложен или их несколько — не находит ничего.
3. **Компонент нельзя править из панели.** Изменить шаблон (текст, цвет, размер), переименовать,
   поправить вложенность можно только с холста до объявления или батчем от агента.
4. **Параметры нельзя задать из панели.** `props` описываются только при `define-component`
   (агентом или через диалог, где объявляется один текстовый параметр `label`). Добавить
   параметр, задать `target`/`property`, поменять значение по умолчанию — нельзя.
5. **Переопределения не видно.** Инспектор показывает поля параметров, но не говорит, какие
   из них переопределены на этом инстансе, и не даёт сбросить одно или все.
6. **Нет вариаций.** Один компонент = один шаблон, поэтому «кнопка primary / secondary / danger»
   — это три разных компонента, между которыми нельзя переключиться на инстансе.
7. **Нет замены компонента** на инстансе, нет дублирования компонента, нет поиска по библиотеке.

### 6.2 Что делаем

**Просмотр.** Карточка компонента получает **превью** — тот же `NodeView`, отрисованный в
миниатюрном «мире» с автомасштабом под рамку превью (200×110). Это переиспользует настоящую
отрисовку, поэтому превью не разойдётся с холстом. Плюс поиск по имени/ключу и счётчики,
плюс подсветка **всех инстансов** компонента на холсте при наведении карточки.

**Выбор и переход.** Клик по карточке выбирает и **центрирует** все инстансы этого компонента
(их id берутся обходом документа, а не поиском среди верхних фреймов). Кнопка «найти» —
зум к первому инстансу.

**Правка шаблона.** Режим «Редактировать компонент»: холст переключается в режим компонента —
рисуется шаблон `component.node` как единственный фрейм, всё остальное скрыто; правки
локальные, «Готово» пишет компонент и возвращает холст. Это правильный путь, но он требует
новой операции записи шаблона (`update-component`) и режима вьюпорта — поэтому выносится в
отдельную фазу.

**Параметры (props) из панели.** Редактор списка параметров: имя, тип (`text/color/number/
boolean/token`), значение по умолчанию, `target` и `property`. `target` задаётся либо текстом,
либо **пипеткой по узлу шаблона** (клик по узлу в превью/схеме подставляет `#Имя` или путь).
Требует операции `update-component`, которая патчит `name`/`description`/`props`/`node`
существующего компонента, не пересоздавая его (сейчас `define-component` перезаписывает ключ
молча — это уже отмечено в BACKLOG как P3).

**Инстанс.** В инспекторе рядом с каждым параметром: метка «переопределено», стрелка сброса
одного переопределения и «сбросить всё»; «вынести в компонент» (записать текущее значение
инстанса в шаблон); «заменить компонент» (выбор из списка с сохранением совпадающих
переопределений).

**Вариации.** Два варианта модели — нужен выбор владельца, потому что он определяет формат
файла и поведение агента.

| | A. Набор вариантов внутри компонента | B. Вариации как отдельные компоненты |
|---|---|---|
| Формат | `components[key] = { node, props, variants: { "size=sm": { node, props } } }`, у инстанса поле `variant` | `components["button/sm"]`, у экземпляров общий префикс или поле `set` |
| Плюсы | один компонент — одно место; переключение варианта на инстансе одним полем; в экспорт идёт одна сущность | не меняет модель компонента вовсе; работает уже сейчас (сегодня так и делают вручную) |
| Минусы | новая ветка в разворачивании, экспорте, валидации и в схеме инструмента | нет переключения на инстансе; нет общего списка вариантов; переименование набора — ручная работа |
| Агент | `design_components action=variant` + `op: variant` | ничего нового |

Рекомендация: **A**, но в минимальном виде — `variants` как словарь «имя варианта → патч
шаблона и `props`», с наследованием от базового шаблона. Тогда «задать вариации» = добавить
ветку, а не собрать второй компонент, и `design_components` получает действия
`variant-add` / `variant-set` / `variant-remove`. Цена — правки в `expandInstance` (schema и
client), в `validateDoc` (вариант без базового узла) и в `export.js` (страница библиотеки
печатает варианты).

## 8. Решения владельца

1. Модель вариаций — **A**: набор вариантов внутри компонента (`variants` + поле `variant` у
   инстанса), см. фазу 4.
2. Направляющие в экспорт не попадают: это редакторская разметка. Зафиксировано в README и
   `ARCHITECTURE.md`.
3. Порядок работ — фаза 2 (удобства редактирования), затем фазы 3–4 (компоненты и вариации).
4. `Shift` при перемещении — **ограничение по оси** (объект скользит строго по X или по Y, вдоль
   направляющей), сетка на время `Shift` в движении выключена: ось важнее шага. У ресайза и
   создания `Shift` по-прежнему шаг 10px.
5. Рамку выделения можно начать прямо по фону контейнера (протяжка выделяет его детей, клик —
   сам контейнер), как в Figma; вход двойным кликом остался.
6. «Объединить в фрейм» создаёт обычный фрейм по габаритам выделения, без авто-раскладки
   (`clip: true`, `layout.mode: none`), — и в панели, и у агента (`group` с `as: frame`).

Открытых вопросов нет.
