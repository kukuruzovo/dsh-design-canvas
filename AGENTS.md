# Design Canvas — проектный слой агента

> Плагин DeepSeek Harness: инструменты агента `design_*` и Figma-подобная панель «Макеты»
> работают с одними файлами `<проект>/.design/*.canvas.json`, поэтому дизайн версионируется
> вместе с кодом приложения.
>
> **Пользовательский канон — [README.md](README.md)**: что умеет плагин, модель документа,
> операции, экспорт, панель, установка. Здесь — только то, что нужно агенту для правок:
> границы слоёв, инварианты, команды и правила сдачи.
> **Внутренний канон — [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md)**: слои, зависимости,
> рецепты расширения, коды ошибок. **Известные дефекты и долги — [docs/BACKLOG.md](docs/BACKLOG.md)**.

## Команды

| Что | Команда |
|---|---|
| Синтаксис всех `.js`/`.mjs` | `npm run check` |
| Проверки ядра, инструментов, контракта клиента и автономного сервера | `npm test` |
| Автономное окно редактора (Playwright, харнесс не нужен) | `npm run test:editor` |
| Окно редактора в tailnet (адрес узла, токен) | `npm run editor:tailscale` |
| Панель в живом DSH (Playwright, нужен токен) | `DSH_WEB_TOKEN=… node smoke-gui.mjs http://127.0.0.1:3080 .gui-shot.png` |
| Демо-холст `demo/` (фикстура панели) | `npm run demo` |
| Эксперты и команда The Agency: сверка с профилем | `npm run agency:check` |
| То же с записью в профиль | `node tools/agency-sync.mjs` |

## Слои и правило границ

| Файл | Слой |
|---|---|
| `schema.js` | модель: нормализация, дерево, токены, компоненты, layout, валидация |
| `store.js` | файлы: реестр проектов, `.design/`, ревизии, корзина, атомарная запись |
| `ops.js` | операции над документом (транзакционный движок) |
| `export.js` | генерация HTML/CSS (чистая, без fs) |
| `service.js` | сценарии: единственное место стыка schema+store+ops+export |
| `tools.js` | 9 инструментов агента — тонкий адаптер |
| `route.js` | HTTP-маршрут `/api/dsh-design-canvas` — тонкий адаптер |
| `client.js` | панель-редактор (React без JSX, браузерный бандл) |
| `standalone.js` | автономный хост: статика оболочки, тот же маршрут на своём порту, токен, tailnet |
| `standalone/` | оболочка окна (`index.html`, `shell.js` — шим контекста, `theme.css`) |
| `vendor/` | React 18 UMD (MIT) — окно не зависит от харнесса и сети |

Зависимости строго линейные: `schema → store/ops/export → service → tools/route → index`;
`standalone.js` подключается к `route.js` сбоку и своей логики не заводит.
Логика живёт в `schema/store/ops/export/service`; `tools.js`, `route.js`, `standalone.js` и
`client.js` только разбирают аргументы и рисуют. Новое правило поведения, продублированное
в адаптере, — дефект.

## Инварианты

1. **Один сервис на две половины.** Инструмент агента и панель идут через `service.js`; правила
   не дублируются между Host и клиентом.
2. **Батч атомарен.** `applyOps` работает на полной копии документа: ошибка в любой операции
   откатывает весь батч, документ на диске не меняется.
3. **Ревизия.** `rev` растёт ровно на 1 за успешную запись; несовпадение `expectRev` → 409
   (обойти можно только `force`). `rev` — поле файла, а не модели документа.
4. **Инстанс — живая ссылка.** Своего содержимого у инстанса нет: `component`, геометрия и
   `overrides`. `children` нормализация не вычищает (чужой файл не должен терять данные), но при
   чтении, отрисовке и экспорте содержимое всегда берётся из шаблона, а непустой массив у инстанса
   попадает в `design_validate` как `instance-children`.
5. **Идентификаторы.** Персистентный id матчит `/^[A-Za-z0-9_-]{1,64}$/`. Дети инстанса получают
   `<instanceId>/<childId>` — этот id существует только в развёрнутом дереве и на диск не попадает.
6. **Токены.** Ссылка — строка `token:<путь>`; исключение — `text.token`: голый путь типографики
   (`text.h1`). Смена токена перекрашивает макет в редакторе и в экспорте.
7. **Клиент панели.** Никаких `import`/`export` и JSX: `require('react')` + `h(...)`, экспорт через
   `window.__ModuleLoader__.load`. Только токены темы `--dsw-*`, цветовые литералы — строкой в JS,
   не в шаблоне `CSS`. У `<style>` обязательны `data-plugin` и `data-plugin-css`.
8. **Защита путей.** Любой путь строится из `ID_RE`-проверенного id и `basename`; наружу
   `.design/` ничего не пишется. В автономном хосте статика отдаётся только по закрытой таблице
   `ASSETS` — путь из запроса в файловую систему не попадает; как только окно видно не только
   с этого компьютера (не-петлевой адрес, `--tailscale`, `--tailscale-serve`), доступ закрывается
   токеном — своим или сохранённым в `$DSH_HOME/design-canvas-token` (права `0600`).

## Стиль кода

- ESM без TypeScript и сборки; 2 пробела, одинарные кавычки, точки с запятой не ставятся.
- JSDoc-блок на каждом экспортируемом символе и на неочевидных внутренних: `@param`, `@returns`.
- Проза — по-русски, идентификаторы — по-английски; инлайн-комментарий только там, где код
  не объясняет причину (историю решения, обход платформы), а не что он делает.
- Ошибки — типизированные классы со `status`/`payload` (`StoreError`, `OpsError`, `ServiceError`);
  `console.*` в библиотечных модулях нет.

## Сдача изменения

1. `npm run check` и `npm test` — зелёные. Правка `client.js` дополнительно требует живого прогона
   панели (`smoke-gui.mjs`): контракт в Node проверяется статически, «работает» — только наблюдение.
2. Новая возможность покрыта хотя бы одной проверкой в существующем стиле (`node:assert/strict`,
   свой tmp-каталог, уборка за собой).
3. Документация синхронизирована в той же задаче: README — если изменилось поведение для человека;
   `docs/ARCHITECTURE.md` — если изменился слой или инвариант; `docs/BACKLOG.md` — если дефект найден,
   но не исправлен. Один факт — в одном месте, остальные ссылаются.
4. Непрогнанное и непроверенное называется прямо. «Должно работать» — не результат.

## Скилы проекта

DSH сканирует `<корень>/.dsh/skills`, поэтому скилы проекта грузятся штатным `skill`.

| Скил | Когда |
|---|---|
| `design-canvas-context` | начало любой задачи в проекте: карта, канон, команды, установка |
| `design-canvas-core` | правка ядра: `schema/store/ops/export/service/tools/route` |
| `design-canvas-panel` | правка `client.js`: слоты, состояние, редактор, темы, локализация |
| `design-canvas-quality` | проверки, регрессии, приёмка, разбор расхождений README↔код |

Глобальные скилы, которые дополняют проектные: `cordis-plugin-development` (плагины DSH),
`agent-experience` (описания инструментов и скилов), `ts-doc-comments` (стиль комментариев),
`code-review`, `diagnosing-bugs`, `webapp-testing` (Playwright).

## Эксперты и команда The Agency

`agency/experts/*.yml` — кастомные эксперты, `agency/teams/*.yml` — команда; проект хранит их как
файлы, а `tools/agency-sync.mjs` переносит в конфиг плагина `agency-agents` профиля
(`~/.dsh/profiles/<профиль>/cordis.patch.yml`), не трогая чужие записи. После правки определения:
`npm run agency:check`, затем `node tools/agency-sync.mjs`.

- Команда **«Разработка Design Canvas»** — 8 ролей: Host-половина, модель документа, панель,
  визуальный язык, ревью диффа, проверки, независимая сверка заявлений, документация.
- Эксперты: **Разработчик плагинов DSH**, **Архитектор визуального редактора**.

Профиль живой: запись в `cordis.patch.yml` подхватывается без перезапуска.

## Установка и перезагрузка

Плагин подключён как `link:` в `~/.dsh/profiles/web/package.json` и перечислен в
`dsh.profile.bundles`. Правки Host-половины подхватываются после перезапуска `dsh web`;
клиентская половина — обновлением страницы, а на лету только при запущенном `pnpm run dev:web`.
`package.json` и `cordis.patch.yml` профиля вручную не правятся — установка идёт через
`plugin_manager` (`install_bundle`), и каждое его действие требует подтверждения человека.
