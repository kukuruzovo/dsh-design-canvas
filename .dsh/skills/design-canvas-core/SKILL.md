# Ядро Design Canvas

Инварианты и границы слоёв — в `AGENTS.md` (уже в контексте). Здесь — процедура правки и то,
что не видно из кода с первого взгляда. Рецепты расширения и коды ошибок — `docs/ARCHITECTURE.md`.

## Шаг 1. Назови слой

| Что меняется | Где живёт логика | Кто ещё обязан это увидеть |
|---|---|---|
| форма узла, токены, layout, компонент | `schema.js` | `ops.js`, `export.js`, `client.js`, `validateDoc` |
| файлы, реестр, ревизии, корзина | `store.js` | `service.js` |
| новая операция над документом | `ops.js` | `tools.js` (`OPS`/`OP_HELP`), `client.js` (если правится человеком) |
| HTML/CSS вывода | `export.js` | — |
| сценарий для агента и панели | `service.js` | `tools.js`, `route.js` |
| аргументы и текст инструмента | `tools.js` | README, `smoke-tools.mjs` |
| HTTP-контракт панели | `route.js` | `client.js`, `smoke-client.mjs`, README |

`tools.js` и `route.js` — адаптеры: если в них появилась логика над деревом, правка в неверном слое.

## Шаг 2. Назови инварианты, которые затрагивает правка

Прочитай раздел «Инварианты» в `AGENTS.md` и перечисли **вслух** те, что могут сломаться. Типичные:
уникальность id, рост ревизии ровно на один, атомарность батча, инстанс без `children` на диске,
`ID_RE` для персистентных id, `token:`-ссылки, согласованность нормализации клиента и сервера.

Правило «четырёх потребителей»: новое поле узла обязано быть понято **операциями, отрисовкой в
панели, экспортом и валидацией**. Если хотя бы один не умеет — правка не готова.

## Шаг 3. Правь и проверяй

1. Стиль — как в соседних файлах: JSDoc на экспортах, проза по-русски, без точек с запятой,
   инлайн-комментарий только про причину.
2. Нормализация: любое внешнее поле проходит `normalize*`; значение по умолчанию сохраняется так,
   чтобы старый `canvas.json` открывался без миграции.
3. Ошибка — типизированный класс со `status`: `StoreError`, `OpsError`, `ServiceError`. Адаптеры
   только пробрасывают её статус в ответ.
4. Проверки — скил `design-canvas-quality`: минимум `npm test`, для клиента ещё живой прогон панели.
5. Документация: изменение поведения для человека → README; слоя или инварианта →
   `docs/ARCHITECTURE.md`; новый найденный дефект → `docs/BACKLOG.md`.

## Ловушки, проверенные по коду

- **`autoW`/`autoH` — поля узла, а не `layout`.** `normalizeNode` сохраняет их только при явном
  значении, `layoutChildren` читает `frame.autoW`; старый `canvas.json` при этом не обрастает новыми
  полями. Поведение закреплено проверками в `smoke.mjs` и описано в README.
- **`rev` — поле файла, а не модели.** `normalizeDoc` его не знает; `design_read mode=full` и
  `GET /canvas?mode=full` возвращают `doc` без `rev`, сам `rev` — соседнее поле ответа.
- **Обрезка детей — поле `clip`, не `style.clip`.** `opAdd` ставит `clip: true` фрейму без явного
  значения; `style.clip` из старых файлов не читают ни экспорт, ни валидация.
- **`set-canvas` проверяет `device`** по `DEVICE_PRESETS`: неизвестное значение даёт 400, а не
  молчаливую подмену на `mobile`.
- **`tokensView`: `replace` и `remove` работают вместе.** Набор, который опустошился бы целиком,
  отклоняется 400 («Набор токенов не может стать пустым») — иначе «удали всё» молча вернуло бы
  дефолтную палитру при следующей нормализации.
- **`align` читает `axis`**, который подменяет ось, выведенную из `mode`. `axis` валидируется:
  неизвестное значение и противоречие с `mode` (`axis: 'y'` при `mode: 'left'`) отклоняются 400, а не
  выравнивают наугад. Проверка — в `smoke.mjs`.
- **Инстанс на диске может нести `children`** — нормализация их не вычищает (чужой файл не должен
  молча терять данные), но содержимое всегда берётся из шаблона, а непустой массив даёт
  `warn instance-children` в `validateDoc`.
- **`add`, `instantiate` и `move` в не-контейнер отклоняются 400** («не может содержать детей»);
  `ungroup` инстанса — 400 с подсказкой про `detach`. До этого нормализация молча выбрасывала детей
  не-контейнера, то есть поддерево терялось.
- **`define-component` перезаписывает существующий `key` молча**; override с объявленным параметром
  и ненайденным `target` пропускается молча.
- **Не используются адаптерами**: `inline` в аргументах `design_export` (панельный `GET /export`
  включает его сам).
- **`design_export` параллелится только при `write: false`** — по умолчанию инструмент пишет файлы
  в `.design/exports/`.
- **Верхние фреймы в экспорте всегда в потоке доски** `.dc-board`, в обоих режимах; режим меняет
  только позиционирование внутри фреймов.
- **`opAdd` сохраняет валидный и свободный id**, иначе генерирует новый; коллизия проверяется дважды.
- **Проверка контраста зависит от размера текста.** Порог — 4.5:1 для мелкого и 3:1 для крупного
  (24px и больше либо полужирный от 18.66px); цвета читаются из hex, `rgb()`/`rgba()` и ссылок на
  токены, полупрозрачный текст смешивается с фоном. Текст без заданного цвета не проверяется:
  панель и экспорт отдают его темой. Проверки — в `smoke.mjs`.
- **Авторские дети инстанса — `warn instance-children`.** Нормализация их сохраняет (данные чужого
  файла не вычищаются), но при отрисовке они игнорируются: без замечания это тихий сток данных.
  Проверка — в `smoke.mjs`.
- **Глубина и объём**: `MAX_DEPTH = 64` (дети обрезаются), `MAX_NODES = 20000` (только валидация),
  холст больше 8 МБ не читается и не записывается (413) — лимит проверяется и на записи, иначе файл
  становился нечитаемым для панели.
- **Проект, найденный по каталогу, берётся в реестр** (`adoptProject` в `store.js`): иначе
  `resolveProject` по id его не знает, и `design_create` / `design_apply` / список холстов падают 404
  на сценарии «клонированный репозиторий с закоммиченной папкой `.design/`». `createCanvas` пишет в
  уже разрешённый проект (`writeCanvasTo`) и не разрешает его второй раз по id.
- **Раскладка потока считает свободное место**: `justify` (`start`/`center`/`end`/`space-between`) и
  `align: 'stretch'` работают, а при `justify !== 'start'` авторский размер по главной оси
  сохраняется. Ту же арифметику повторяет панель (`layoutFrame`), паритет проверяет `smoke-client.mjs`.

## Коды ошибок

| Код | Когда |
|---|---|
| 400 | недопустимый id холста или метки корзины, каталог не проект, чужой `format`, неизвестное действие, ошибка операции в батче (payload `{opIndex, op}`) |
| 404 | нет холста, проекта, каталога, записи корзины |
| 409 | холст уже существует, ревизия устарела (`payload {rev, expected}`) |
| 413 | холст больше 8 МБ или тело запроса больше 16 МБ |
| 500 | повреждённый JSON холста, в записи корзины нет файла |

## Рецепт: новая операция

1. `ops.js`: обработчик `op<Имя>` + запись в `OPS`; возвращай `{...}` результат для отчёта
   инструменту; ошибку бросай через `fail`, она обернётся в `OpsError` с индексом операции.
2. `tools.js`: описание в `OP_HELP` — оно попадает в схему `design_apply` и `design_create`
   автоматически (`OP_SCHEMA`).
3. `client.js`: если операция нужна человеку, добавь действие в панель (скил `design-canvas-panel`).
4. README: таблица операций; `smoke.mjs` — проверка поведения и откат при ошибке в середине батча.

## Рецепт: новый инструмент агента

1. `service.js` — view-функция, возвращающая обычный JSON-объект (он же тело HTTP-ответа).
2. `tools.js` — `ctx.tools.register` с `parameters.additionalProperties: false`, `output.render`
   через `textBlocks` и `presentCall`; описание пиши как контракт для модели (скил `agent-experience`).
3. `route.js` — маршрут, если функция нужна панели.
4. `smoke-tools.mjs` — точный список имён инструментов и сквозной цикл; README — таблица инструментов.
